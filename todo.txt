Just completed

* §1.6 `ImportService` no longer swallows unrelated database failures. The
  atomic commit unit (image row + path + faces) was wrapped in
  `catch (SQLException e)` and treated as "another worker imported this first"
  on the strength of one `imageDao.exists(hash)` check alone, so *any*
  failure of that transaction — NOT NULL, FOREIGN KEY, a trigger abort,
  `SQLITE_FULL`, a disk error — became "new path recorded" and the import
  reported success for a file whose faces were never stored. The guard is
  narrow (the hash must appear between the existence check and the catch),
  but that is precisely the window the branch exists for, so the collision
  path and the real-failure path were indistinguishable.
  The backlog proposed catching `SQLIntegrityConstraintViolationException` /
  `SQLTransactionRollbackException`; that is impossible with sqlite-jdbc
  3.45.1.0 and would have been dead code. Every failure the driver builds
  goes through `DB.newSQLException`, so it is always an
  `org.sqlite.SQLiteException extends SQLException` whose only constructor
  calls `super(message, null, code & 0xff)`: SQL state always `null`, error
  code truncated to its low byte, and neither JDBC-standard class is ever
  instantiated. `getErrorCode()` is 19 (`SQLITE_CONSTRAINT`) for *every*
  constraint class, so it cannot discriminate either. What survives is the
  extended result code, read through one predicate —
  `SqliteErrors.isDuplicateContentConflict`, in the `db` package because a
  driver detail belongs at the JDBC/SQLite boundary and `ImportService`
  should stay driver-agnostic.
  The correction that mattered most is the code list. A duplicate on
  `images.hash` arrives as `SQLITE_CONSTRAINT_PRIMARYKEY` (1555), **not**
  `SQLITE_CONSTRAINT_UNIQUE` (2067): SQLite reports the constraint that was
  *declared*, and even its message text ("UNIQUE constraint failed:
  images.hash") disagrees with its own code. Only the separate unique index
  on `faces (image_hash, bbox_x, bbox_y, bbox_w, bbox_h)` raises 2067. So
  the predicate accepts PRIMARYKEY **and** UNIQUE — accepting UNIQUE alone,
  as proposed, would have killed the very collision path the branch exists
  for, silently and without any test complaining, because lines 215-239 had
  zero coverage. Everything else now propagates: NOT NULL (1299), FOREIGN
  KEY (787), trigger abort (1811), CHECK (275), `SQLITE_ERROR` (1), FULL,
  I/O, corruption, and any non-driver `SQLException`. The existence check
  stays as the second condition of the same one-line guard: the result code
  names the failure, the existence check is the second line of defence for
  the unique-index case and for a hash inserted by the video/frame path.
  Pinned by the new `SqliteErrorsTest` (16 cases — 9 unit cases on the
  classification, 7 driving a real `Database.inMemory()` to prove the driver
  really produces each code, incl. one that documents why `getErrorCode()`
  and the SQL state cannot be used) and 2 new `ImportServiceTest` cases:
  the collision path, which had no coverage at all and is what a naive
  narrowing silently kills, and the unrelated-failure case, red against the
  unmodified service with `expected: <1> but was: <0>` on `errors()` — the
  swallowed failure, named. Both stage the race from a new one-shot
  `FakeFaceAiEngine.withDetectionHook` so the competing row lands in the
  window between the existence check and the commit. Mutation-verified both
  ways: a predicate that always returns `true` (the original behaviour)
  fails 11 cases including that one; one that always returns `false` fails 5
  including the collision case.

* §3 The path-prefix filters can use an index. `substr(path, 1,
  length(?)) = ?` cannot be served from any index, so both the folder
  filter of the tagging views and the remove-by-folder preview walked
  every stored path; they now match with the lexicographic range
  `path >= ? AND path < ?`. The two bounds come from one shared,
  package-private `PathPrefix` value object, so the successor can no
  longer be computed twice, differently. The bound increments the last
  *code point*, not the last UTF-16 unit: SQLite compares UTF-8, which
  is order-preserving, so a code-point increment always orders right,
  whereas breaking a surrogate pair yields a lone low surrogate that the
  JDBC driver silently substitutes — a bound that is too small, i.e.
  `DataRemovalDao` under-deleting. A prefix of only U+10FFFF has no
  successor at all, so it degrades to `>=` alone. Semantics are
  unchanged: still a plain, byte-wise, case-sensitive string prefix, so
  `/photos/family` keeps matching `/photos/family-archive/` — the
  sibling / near-miss cases in both DAO tests pin exactly that.
  `idx_image_paths_path` and `idx_video_paths_path` serve it, declared
  in the baseline schema *and* in the new version-3 migration
  (`SCHEMA_VERSION` 2 -> 3), so an existing library gains them on the
  next open; `createPathIndexes` is shared by both paths so the two
  cannot drift. Pinned by the new `PathPrefixTest` (11 cases, no
  database), 4 new `DataRemovalDaoTest`, 5 new `FaceDaoTest` and 2 new
  `DatabaseTest` cases, plus the new `QueryPlans` test seam, which reads
  `EXPLAIN QUERY PLAN` and asserts `SEARCH <ref> USING ...` rather than
  the exact plan text. Mutation-verified: a `(char)(c + 1)` successor
  fails 5 `PathPrefixTest` cases, and dropping `idx_video_paths_path`
  fails the plan test with `SCAN video_paths` plus both `DatabaseTest`
  index cases.
* The follow-on item on the placeholder count is closed too:
  `PATH_FILTER_PLACEHOLDERS`, `FaceDao.bindPathFilter` and
  `DataRemovalDao.bindPrefix` are gone. A hand-maintained count of `?`
  placeholders next to a hand-maintained binder *is* the defect, so both
  went away with the `substr` form: `PathPrefix.bind(ps, firstIndex)`
  binds one range and returns the next index, which is what makes the
  fragment and the bound values impossible to desynchronize.

* §1.5 Re-exporting a person to the same folder no longer aborts with
  `FileAlreadyExistsException`. `Files.copy` now passes `REPLACE_EXISTING`,
  which is what the `Files.write` on the thumbnail branch two lines below
  already did by default — so the two branches finally agree and a second
  export refreshes the copies instead of failing. Overwriting is the
  deliberate choice over suffixing: `uniqueDestination` exists to stop one
  *run* from writing two different originals onto one name, and the export
  folder is a derived copy, not the library. Pinned by 2 new
  `FaceToNameServiceExportTest` cases — the first was red against
  unmodified code with `FileAlreadyExistsException: ...\out\photo.jpg`
  while the thumbnail case already passed, which is exactly the
  inconsistency the item described (so no mutation was needed here).
* §1.9 Shutdown no longer leaks. `stop()` had three unguarded `close()`
  calls, and since `importService.close()` and `faceAiService.close()`
  both release native resources *and rethrow the first failure*, one
  throw skipped the rest — including `database.close()`, leaking the
  SQLite handle. Both this and the import-worker construction loop (where
  a failure on the 9th `FaceAiService` leaked the 8 already built — and
  which matters more than it looks, because JavaFX does **not** call
  `stop()` when `start()` throws) now go through one package-private
  static `FaceSortApp.closeAll(AutoCloseable...)`: close everything in
  order, skip nulls, rethrow the first failure with the later ones
  attached as suppressed. Nothing skipped, nothing swallowed.
  A static on the app class keeps it next to both call sites and is what
  makes it headlessly testable — loading `FaceSortApp` pulls in no
  toolkit. Pinned by the new `FaceSortAppTest` (6 cases), mutation-
  verified: making `closeAll` stop at the first failure (the original
  behaviour) fails 3 of them with `expected: <[importService,
  faceAiService, database]> but was: <[importService]>`.
* §1.8 A view's mutable "active name" is no longer read off the background
  thread. Three sites had the defect: `ViewView.untagFaces`,
  `FaceNameView.onTagSelected` and — worst — `FaceNameView.onRename`, which
  could rename the *wrong person* (a destructive write) if you picked
  another name while the rename was in flight. All three now bind their work
  through the new package-private `NameBoundWork.forSelectedName`, which
  snapshots the selection once, synchronously, on the calling thread and
  hands back both the frozen `NameRecord` and the deferred work. The task
  body runs the bound work; the success handlers report and refresh the
  bound name, so nothing can be redirected after the click. The rename
  handler now only adopts the renamed record while that name is still the
  selected one, so you are not yanked back if you moved on.
  `NameBoundWork` contains no `javafx.concurrent.Task` on purpose: a `Task`
  needs an initialized JavaFX toolkit, so a Task-free seam is what makes
  this pinnable headlessly. Pinned by the new `NameBoundWorkTest` (5
  cases), mutation-verified: resolving the selection inside the deferred
  work — exactly the original bug — fails 2 of them with `expected:
  <untagged from Alice> but was: <untagged from Bob>`.
* §1.2 A failed video import no longer poisons the video — the frame loop
  is wrapped in `try/catch (Exception | Error)`, and a failure now undoes
  the registration via the new `VideoDao.delete(hash)`, so the next import
  retries the video instead of skipping it as "already imported" with zero
  frames. The compensating delete is deliberate rather than one big
  transaction: the loop runs ffmpeg + detection per frame and must not
  hold the DB connection monitor across that work. Frame *images* are
  kept — they are content-addressed and shared with photos, so the retry
  reuses them. A cleanup failure is logged and attached to the original
  as suppressed, so the real cause still surfaces. Pinned by 2 new
  `VideoImportServiceTest` cases (verified failing first: `expected:
  <false> but was: <true>` on `videoDao.exists`) and 3 new `VideoDaoTest`
  cases (mutation-verified: neutering the DELETE fails 2 of them).
* §1.7 `RemoveByPrefixDialog` can no longer get stuck disabled — the
  preview success handler returned before `setBusy(false)` on a `null`
  estimate, leaving the dialog with no way back. The handler body is
  now `applyScanResult(Estimate, ScanPresenter)`, which releases the busy
  state first and unconditionally; a `null` estimate takes the normal
  "nothing to remove" path. The new `ScanPresenter` interface is a real
  test seam, so `RemoveByPrefixDialogTest` (3 cases) pins the `null` path
  headlessly — verified failing against the original ordering before the
  fix. First `ui/` class to get coverage outside the three pre-existing
  ones.
* §1.3 `AppConfig.save` is atomic — a failed or interrupted save can no
  longer leave a truncated `facesort-config.json` that stops the app from
  starting. Staged in a sibling temp file + `ATOMIC_MOVE`, mirroring
  `UpdateChecker.writeCacheAtomically`; the temp file is cleaned up in a
  `finally`.
* §1.4 `AppConfig.load` ignores unknown properties — `@JsonIgnoreProperties`
  on `ConfigModel`, so a hand-edited, stale or foreign config file loads
  with the known settings plus the defaults for the rest.
  Both pinned by three new `AppConfigTest` cases, written first: the
  failed-write test reproduced the exact truncated-at-`maxImportThreads`
  file before the fix.
