# FaceSort — Improvement Todo List

- [x] Fix ImportService swallowing unrelated database failures - narrow collision handler to SQLIntegrityConstraintViolationException/SQLTransactionRollbackException (ImportService.java:225-239) - done, but not the way the item proposed: that narrowing is impossible with sqlite-jdbc 3.45.1.0 and would have been dead code. Every failure the driver builds goes through `DB.newSQLException`, so it is always an `org.sqlite.SQLiteException extends SQLException` whose only constructor calls `super(message, null, code & 0xff)` — `getSQLState()` is always `null`, `getErrorCode()` is the extended code truncated to its low byte (a verified `19`/`SQLITE_CONSTRAINT` for *every* constraint class, so it cannot discriminate), and neither `SQLIntegrityConstraintViolationException` nor `SQLTransactionRollbackException` is ever instantiated. The handler therefore still catches `SQLException` and narrows the *predicate* to the extended result code, via the new `SqliteErrors.isDuplicateContentConflict` in the db package (the driver detail is the db layer's business; the service stays driver-agnostic). What the item got wrong is the code list, and the correction matters: a duplicate on `images.hash` arrives as `SQLITE_CONSTRAINT_PRIMARYKEY` (1555), **not** `SQLITE_CONSTRAINT_UNIQUE` (2067) — SQLite reports the constraint that was *declared*, and the message text ("UNIQUE constraint failed: images.hash") disagrees with the code. Only the separate unique index on `faces (image_hash, bbox_x, bbox_y, bbox_w, bbox_h)` raises 2067. So the predicate accepts PRIMARYKEY **and** UNIQUE; accepting UNIQUE alone would have broken the collision path the branch exists for. Everything else now propagates: NOT NULL (1299), FOREIGN KEY (787), trigger abort (1811), CHECK (275), `SQLITE_ERROR` (1), FULL, I/O, corruption — and any non-driver `SQLException`. The `imageDao.exists(hash)` check stays as the second condition of the same guard: the code names the failure, the existence check is the second line of defence for the unique-index case and for a hash inserted by the video/frame path. Pinned by the new `SqliteErrorsTest` (16 cases: 9 on the classification, 7 driving a real `Database.inMemory()` to prove the driver really produces those codes, incl. one that documents why `getErrorCode()`/SQL state cannot be used) and 2 new `ImportServiceTest` cases — the collision path, which had **zero** coverage before and is exactly what a naive narrowing silently kills, plus the unrelated-failure case that was red against the unmodified code with `expected: <1> but was: <0>` on `errors()`. Mutation-verified both ways: always-true fails 11 (incl. case B), always-false fails 5 (incl. case A).
